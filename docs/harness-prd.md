# PRD: 질의응답 기반 이커머스 제작 하네스

작성일: 2026-09-21  
상태: Machine Code 적용 · S1 구현·검증 완료 · S2 설계안 확인 대기  
목표·단계·승인 기록: [목표 문서](harness-goals.md)

## 1. 문제와 근거

현재 플러그인은 단일 `machinebot-ecommerce-studio` 스킬 안에 추천부터 여섯 제작 분기의 기획·생성·검수를 담고 있다. 추천과 마스터 제품컷 개념은 이미 존재하지만, 제품 자산 준비와 상세페이지 제작을 독립적으로 시작·종료하고 결과를 인계하는 계약이 명확하지 않다.

확인한 기준:

- [현재 실행 스킬](../plugins/machinebot-ecommerce-studio/skills/machinebot-ecommerce-studio/SKILL.md): 탐색·분기 지정·수정·현지화 진입과 최소 입력 수집.
- [제작 분기](../plugins/machinebot-ecommerce-studio/skills/machinebot-ecommerce-studio/references/branches.md): 기존 여섯 분기·수량과 라이트/풀.
- [이미지 제작](../plugins/machinebot-ecommerce-studio/skills/machinebot-ecommerce-studio/references/image-production.md): 필요할 때만 마스터 누끼 생성, 최종 패널 전체 렌더링.
- [기존 기획 테스트](../validation/forward-test-1.9.0.md): 마스터 제품컷 고정과 별도 누끼 생성 의무 사이의 해석 여지가 기록됨. 신규 이미지 품질 검증 자료는 아님.
- [기존 행동 평가](../validation/behavior-evaluation.md): 명시 요청 직행, 사실 통제, 상세페이지 규격, 범위·승인 회귀 기준.

추천 수량도 정리할 필요가 있다. 현재 실행 스킬에는 `2~3개 분기와 전체 패키지`와 `최대 3개`가 함께 있다. 이번 제안은 전체 패키지를 포함해 총 2~3개로 통일한다.

## 2. 사용자와 핵심 사용 사례

| 사용자 상태 | 하고 싶은 일 | 제품이 제공할 경험 |
|---|---|---|
| 처음 상품을 준비함 | 무엇부터 만들지 결정 | 보유 자료·목적에 맞는 추천과 선택 |
| 원본 사진만 있음 | 제품이 명확하게 보이는 이미지 확보 | 제품 사진·누끼만 독립 제작 |
| 제품 기준컷은 있음 | 고객이 쓰는 모습을 보여주기 | 기존 제품 기준을 유지한 연출컷 제작 |
| 사진과 정보가 충분함 | 상세페이지 완성 | 자산 재제작을 강제하지 않고 상세페이지 직행 |
| 전체가 필요함 | 판매 이미지 전체 준비 | 라이트/풀 선택과 승인한 범위의 순차 실행 |
| 기존 결과가 있음 | 일부만 수정하거나 다음 제작에 활용 | 기존 사실·자산을 재사용하고 변경 범위를 한정 |

## 3. 최종 스킬 구조 — 제안

플러그인은 하나로 유지하고 그 안에 진입 스킬 1개와 제작 스킬 5개를 둔다. 아래 이름은 제안이며 각 분리 단계에서 확정한다. 현재 존재하는 실행 스킬은 진입 스킬 1개뿐이다.

| 역할 | 스킬 이름 제안 | 독립 산출물·책임 | 도입 단계 |
|---|---|---|---|
| 시작·진단·조합 | `machinebot-ecommerce-studio` | 질의응답, 추천, 선택한 스킬 연결, 전체 패키지 진행 | S1부터 점진 전환 |
| 제품 사진·누끼 | `machinebot-product-cutout` | 원본 확인, 제품 기준 잠금, 투명 PNG, 요청한 배경 변형 | S2 |
| 연출·실사용컷 | `machinebot-lifestyle` | 제품 장점·사용 상황을 보여주는 독립 장면 세트 | S3 |
| 상세페이지 | `machinebot-detail-page` | 소구·카피·패널 구성 승인, 생성·검수, 외국어 원본 현지화 | S4 |
| 썸네일 | `machinebot-thumbnail` | 메인·서브 썸네일 | S5 |
| 효용·기능 시각화 | `machinebot-benefit-visual` | 확인된 기능·구조의 설명 이미지 | S6 |

전체 패키지는 여섯 번째 **결과물 분기**이며 별도 생성 엔진을 만들지 않는다. 진입 스킬이 필요한 제작 스킬을 직렬로 연결한다. 공통 제약·근거·검수 규칙은 하나의 기준 문서를 참조하고, 각 제작 스킬의 직접 진입에서도 필요한 공통 규칙을 읽는다.

하위 스킬의 `description`과 진입 스킬의 책임을 구분해 중복 선택을 줄인다. 순차 이전 중에는 분리한 기능만 새 스킬로 연결하고 나머지는 기존 실행 경로를 유지한다. 존재하지 않는 스킬을 호출하거나 제작 가능하다고 안내하지 않는다.

## 4. S1: 첫 구현 범위

### 포함할 것

1. 기존 스킬에서 탐색과 명시 요청을 먼저 구분한다.
2. 탐색에는 목적·보유 자료·이번 범위를 판단할 최소 질문을 제공한다.
3. 답변과 실제 자료에 기반해 총 2~3개 제작 타입을 제안한다.
4. 사용자가 선택하면 선택 범위와 이미 받은 정보를 기존 제작 경로에 넘긴다.
5. 명시 요청·수정·외국어 현지화는 해당 경로로 바로 연결한다.
6. 아래 A01~A06·A09~A11·A15~A17을 대화와 경로 회귀 사례로 검증한다. 이 단계의 상세페이지 검증은 기획·연결 동작이며 실제 생성 검수가 아니다.

### 뒤 단계로 남길 것

- 독립 제작 스킬 파일 생성과 공통 기록의 파일 저장 구현.
- 이미지 생성 방식·기본 수량·상세페이지 규격 변경.
- 전체 패키지 실행 구조 재작성과 기존 참조 문서의 대규모 이동.

### 수정 예상 파일

- 기존 `SKILL.md`: 시작 판별·질문·추천·기존 분기 연결.
- 기존 스킬의 `references/intake-routing.md`: 질문·추천·연결 기준을 담을 신규 참조 문서. S1 승인 후 생성하고 `SKILL.md`에 읽는 조건을 연결한다.
- 기존 `agents/openai.yaml`: 진입 설명과 시작 프롬프트 일치.
- `references/branches.md`: 추천 수량·연결 설명 일치가 필요한 부분.
- `validation/behavior-evaluation.md`와 해당 버전 검증 기록.
- 배포 동기화에 필요한 manifest, 루트·플러그인 README, CHANGELOG, 버전 링크가 있는 배포 안내, 새 ZIP·체크섬.

기존 미커밋 변경을 보존하고 해당 단계의 요구사항과 직접 관련된 부분만 편집한다.

## 5. 시작 대화와 추천 요구사항

### R1. 먼저 이미 주어진 정보를 읽는다

사진·문서·요청 문장으로 답을 알 수 있으면 질문하지 않는다. 한 번에 기본 1~3개의 짧은 질문을 하되, 자료 없이 타입을 확정해야 하는 상황이면 필요한 답을 기다린다. 선택형 질문 UI가 있으면 사용하고, 없으면 짧은 번호형 질문으로 같은 흐름을 제공한다. 특정 호스트 전용 UI를 필수 의존성으로 삼지 않는다.

### R2. 질문은 결과 선택에 영향을 주는 것부터 묻는다

| 질문 축 | 사용자에게 보여줄 예시 | 질문을 생략하는 조건 |
|---|---|---|
| 당장 필요한 결과 | 상품 등록용 이미지 / 사용 장면 / 상세페이지 / 잘 모르겠음 | 요청에 결과물 종류가 명확함 |
| 보유 자료 | 원본 사진 / 누끼 / 연출 사진 / 기존 상세페이지 / 아직 없음 | 첨부 자료를 확인해 판단 가능 |
| 이번 범위 | 필요한 이미지부터 / 전체 판매 이미지 준비 | 수량·범위를 이미 지정함 |

제품명·타깃·판매 채널도 추천을 바꿀 때만 보충 질문한다. 상세페이지용 전체 스펙을 누끼 제작의 진입 조건으로 요구하지 않는다. 스타일·색감 등 세부 제작 질문은 선택한 스킬에서 필요한 때 묻는다.

### R3. 추천은 이유와 산출물이 있어야 한다

- 추천 수는 전체 패키지를 포함해 총 2~3개. 적합한 선택이 하나로 확정된 명시 요청은 메뉴를 만들지 않는다.
- 가장 적합한 하나에 `추천` 표시를 붙인다.
- 각 항목에 타입, 현재 자료와 연결한 이유, 산출물 수·종류, 필요한 추가 자료를 설명한다.
- 후보를 만들기 위해 부적합한 분기나 근거 없는 기능 효과를 제안하지 않는다. 현재 자료에서 권할 수 있는 분기가 하나뿐이면 그 이유를 설명한다.
- 범위를 정하지 못한 사용자의 선택을 기다린다. 질문에 대한 무응답을 제작 승인으로 처리하지 않는다.

추천 예시 — 제품 전체가 보이지만 배경이 복잡한 사진을 가진 가상 사용자:

> 1. **제품 기준컷·누끼 — 추천:** 제품 윤곽과 색상을 확인한 투명 PNG부터 준비합니다. 기본 1~4장이며, 현재 사진에 보이지 않는 각도는 추가 원본이 필요합니다.
> 2. **연출·실사용컷:** 지금 확인되는 제품 모습으로 사용 상황을 보여줍니다. 기본 4~10장이며 실제 사용 방식과 원하는 장면을 확인합니다.
> 3. **상세페이지:** 제품 정보와 구매 이유를 정리해 6·8·10장 중 구성안을 제안합니다. 구성·사용법 등 필요한 사실을 확인한 뒤 구성 승인을 받습니다.

이는 대화 형식 예시다. 실물 사진이 없어도 제품을 정확히 복원할 수 있다는 약속이나 모든 제품에 동일한 세 후보를 제시하라는 규칙이 아니다.

### R4. 지정 요청은 바로 연결한다

- “누끼 한 장만”: 제품 기준과 출력 조건만 확인한 뒤 누끼 경로로 이동한다.
- “연출컷 4장”: 사용 상황과 필요한 근거만 보완한다.
- “8장 상세페이지”: 제품 정보와 패널 구성을 확인한다. 전체 메뉴나 별도 연출컷 구매를 요구하지 않는다.
- “중국어 상세페이지 ZIP을 한국어로”: 기존 현지화 분석 경로를 유지한다.
- “이 컷 배경만 바꿔”: 기존 제품·목적을 유지한 부분 수정으로 처리한다.

S1에서는 모두 기존 실행 경로를 사용한다. 이후 해당 스킬이 분리되면 연결 대상만 바꾸고 사용자가 제공한 정보를 유지한다.

## 6. 제품 기준과 자산 인계 — S2 전 설계 확인

### R5. 공통 기록의 내용

파일 저장 방식은 아직 확정하지 않는다. S1은 대화 안의 짧은 제작 브리프로 연결하고, S2에서 아래 내용을 프로젝트별 `product-context.json`에 저장하는 방안을 제안한다. 파일 저장이 없는 호스트에서는 같은 항목을 인계 요약으로 전달한다. 별도 데이터베이스는 도입하지 않는다.

| 항목 | 반드시 구분할 내용 |
|---|---|
| 제품 식별 | 제품명·모델·옵션. 같은 제품인지 불명확하면 확인 필요 표시 |
| 원본 자료 | 원본 ID·파일 위치와 역할: 제품 / 스타일 / 브랜드 / 사실 근거 |
| 제품 잠금 | 보존할 형상·색·로고·라벨·구조, 확인되지 않은 면과 부위 |
| 사실·주장 | 확인된 정보와 근거 ID, 확인 필요 정보, 허용·금지 주장 |
| 제작 브리프 | 선택 분기·수량·용도·사용자 제약·필요한 소구·장면 |
| 생성 자산 | 자산 ID·실제 파일·종류·크기·참조 원본·담당 장면 |
| 검수 | 미검수 / 통과 / 수정 필요와 직접 확인한 내용 |
| 선택·승인 | 선택 범위, 상세·패키지 구성 승인 여부와 실제 사용자 응답 |
| 다음 작업 | 납품 완료 범위, 남은 자료, 사용자가 요청한 후속 작업 |

미검수 자산을 검수 통과한 기준컷처럼 넘기지 않는다. 원본은 유지하며, 생성 자산이 새로운 제품 사실의 근거가 되지 않는다. 원본 파일이 없거나 접근할 수 없으면 재첨부를 요청하고 기억만으로 제품을 재현하지 않는다.

### R6. 조건부 선행 작업

- 원본 사진이 충분하면 그것을 제품 기준으로 고정하고 바로 선택한 제작을 시작한다.
- 배경 제거가 필요하면 확인 가능한 제품 범위의 누끼를 만든다. 누끼 생성은 숨겨진 뒷면·내부를 복원하는 절차가 아니다.
- 기본 누끼는 투명 PNG 1~4장. 흰 배경이나 그림자 버전은 용도에 따른 변형으로 기록하고 새 각도·새 장면 수에 중복 산입하지 않는다.
- 단순 누끼 요청에 전체 판매 소구 기획을 요구하지 않는다.
- 연출 스킬은 원본 또는 검수한 누끼를 입력으로 받을 수 있다. 누끼를 필수 선행 스킬로 만들지 않는다.
- 단독 작업이 완료되면 산출물을 전달한다. 후속 선택을 제안할 수 있지만 요청하지 않은 연출·상세페이지 생성을 시작하지 않는다.

## 7. 상세페이지와 패키지 요구사항

### R7. 상세페이지는 독립 제작

- 원본 제품 사진과 충분한 정보만으로 직접 시작할 수 있다.
- 기존 누끼·연출컷이 있으면 원본과 검수 기록을 함께 확인하고 적합한 참조로 사용한다.
- 제품 특징 → 고객 가치 → 근거 → 메시지 → 장면을 연결하고 패널 구성을 한 번 승인받는다.
- 상세페이지에 필요한 사용 장면과 효용 시각화는 해당 패널 제작에 포함한다. 별도 납품할 이미지가 필요하지 않으면 독립 연출 세트의 추가 생성을 강제하지 않는다.
- 자산 준비와 최종 패널 제작을 구분한다. 독립 납품용 누끼·연출 이미지는 가능하지만, 최종 패널을 위한 텍스트 없는 베이스와 별도 글자 레이어를 만드는 경로는 금지한다.
- 최종 패널은 제품·장면·효과·확정 카피를 한 번의 호스트 이미지 생성 또는 편집 호출에서 함께 렌더링한 한 장이어야 한다. 오탈자 수정도 전체 패널 편집·재생성으로 처리한다.
- 6·8·10장, 기본 1080 × 2160px, 최소 세로 2000px, 마지막 FAQ를 유지한다. 외국어 현지화와 기존 근거·장면 다양성 검수도 유지한다.

### R8. 전체 패키지는 조합 실행

- 기존 라이트/풀 수량은 [분기 문서](../plugins/machinebot-ecommerce-studio/skills/machinebot-ecommerce-studio/references/branches.md)를 기준으로 유지한다.
- 사용자가 범위와 구성을 선택·승인하면 그 안의 제작은 매 스킬 전환마다 메뉴를 반복하지 않고 직렬로 진행한다.
- 보유 자산을 재사용할 때는 적합성과 실제 검수 상태를 확인하고 승인할 납품 목록에 반영한다. 재사용 때문에 기본 수량·범위가 달라지면 변경 내용을 먼저 확인받는다.
- 한 이미지를 여러 용도로 사용한 것과 새 이미지를 생성한 것을 구분한다. 같은 컷을 독립된 새 연출 수로 중복 계산하지 않는다.

## 8. 유지할 제약과 실패 처리

- 범위는 기존 여섯 커머스 결과물에 한정한다. 포스터·캐릭터·게임·UI 등을 새 분기로 추가하지 않는다.
- 효능·인증·수치·리뷰·비교 우위·의학적 주장과 실제 제품의 보이지 않는 구조를 만들지 않는다. 시각 효과에도 같은 기준을 적용한다.
- 실물 사진이 없으면 동일 제품 재현이 불가능함을 알리고 필요한 자료 또는 명시적인 콘셉트 시안 범위를 확인한다.
- 호스트 이미지 기능이 없으면 제작 명세·프롬프트까지만 제공하고 실제 생성 완료로 표시하지 않는다.
- 이미지를 직접 열어 확인하지 못했으면 검수 완료로 표시하지 않는다. 잘못된 누끼나 변형된 제품은 이후 단계의 기준으로 전파하지 않는다.
- 결정적 후처리는 리사이즈·파일명·연결·압축처럼 픽셀 내용을 새로 그리지 않는 범위다. 별도 코드 텍스트 합성은 도입하지 않는다.
- 동일 품질 문제가 두 번 반복되면 실패 상태·원인·가능한 대안을 설명한다. 자료 부족으로 유효한 FAQ나 장수를 채울 수 없으면 부족한 근거와 시안 상태를 밝힌다.
- 개발 단계에서 승인한 설계 범위를 바꿔야 하면 제안을 갱신해 사용자에게 확인받는다. 이미 승인한 범위의 오류 수정은 계속 진행한다.

### 검증 수준

1. **문서 대조:** 진입·참조·산출물·규격 사이의 모순과 링크를 확인한다.
2. **대화 실행:** 시나리오 입력으로 첫 응답과 후속 선택 처리를 실제 작성·기록한다. 기대 문구 복사나 키워드 일치만으로 통과시키지 않는다. 독립 평가가 가능하고 허용되면 별도 평가자를 사용하되 이번 구현 작업을 병렬로 분할하지 않는다.
3. **실제 생성·시각 검수:** 각 제작 스킬 분리 단계에서 적절한 실제 제품 자료로 결과를 생성·열람한다. 실물 참조가 필요한 시점에 자료를 확인받는다. 실행하지 못하면 해당 품질 검증은 미완료로 남기고 그 단계를 완전 검증 완료라고 보고하지 않는다.
4. **패키지 검사:** 변경된 모든 스킬에 `quick_validate.py`, 플러그인에 `validate_plugin.py`를 실행한다. 원본과 새 ZIP의 별도 압축 해제본 모두 검사하고 링크·버전·ZIP 최상위 폴더·파일 일치·SHA-256을 확인한다.

기존 단일 스킬의 검사 명령:

```powershell
$env:PYTHONUTF8 = "1"
python "$env:USERPROFILE\.codex\skills\.system\skill-creator\scripts\quick_validate.py" "plugins\machinebot-ecommerce-studio\skills\machinebot-ecommerce-studio"
python "$env:USERPROFILE\.codex\skills\.system\plugin-creator\scripts\validate_plugin.py" "plugins\machinebot-ecommerce-studio"
```

스킬 분리 후에는 새로 생긴 각 스킬에도 첫 검사를 반복한다. 기존 배포 ZIP과 `validation/package-check*/` 스냅샷은 덮어쓰지 않는다. 문서만 추가하는 S0은 배포 콘텐츠 변경이 아니므로 버전·ZIP 생성 없이 문서 링크와 기존 파일 보존을 검사한다.

## 10. 현재 컨펌 안건과 다음 행동

사용자가 지정한 `techtreecoltd/machine-code`를 설치했다. 개발은 아래 §11의 Machine Code 운영 방식으로 진행하며, 설치 승인을 제품 동작 설계 전체의 승인으로 확대하지 않는다.

**승인된 범위: 2026-09-21 사용자 확인에 따라 S1만 먼저 구현한다.** 공수는 [산정 문서](harness-effort-estimate.md)에서 개발 작업과 개별 상세페이지 제작량을 구분한다.

- 사용자에게 부족한 정보만 기본 1~3개 질문한다.
- 탐색 추천은 전체 패키지를 포함해 총 2~3개로 제시한다.
- 명시 요청은 바로 기존 제작 분기로 연결한다.
- 누끼·연출·상세페이지 독립 스킬 생성은 다음 단계에서 각각 설계를 확인받고 진행한다.

대안은 S1에 제품 사진·누끼 분리까지 포함하는 것이다. 이 경우 첫 변경에 공통 기록 형식·원본 대조·실제 누끼 생성 검증까지 필요해 범위가 커진다. 작은 범위로 시작하자는 요청에 맞춰 추천안으로 제안한다.

S1의 구현·검증·배포 결과는 [1.10.0 검증 기록](../validation/release-1.10.0-validation.md)에 남겼다. 다음은 S2의 제품 기준컷 범위와 공통 기록 예시를 확인받는 단계다.

S2 제안은 `machinebot-product-cutout` 독립 스킬로 원본에 보이는 제품의 투명 PNG 1~4장을 만들고, 선택한 경우 흰 배경 변형을 제공하는 것이다. 검수한 원본 연결·제품 잠금·허용 사실·자산 상태를 `product-context.json`에 기록해 다음 연출·상세페이지 작업이 이어 받게 한다. 흰 배경 변형을 새 각도로 세지 않으며, 단독 누끼만 요청하면 그 결과로 종료한다. 정확한 파일 위치와 필드·실제 검증에 사용할 제품 자료는 S2 진입 시 확정한다. 아직 해당 스킬이나 저장 동작을 구현하지 않았다.

## 11. Machine Code 기반 개발 운영

기준 저장소는 [techtreecoltd/machine-code](https://github.com/techtreecoltd/machine-code)다. 설치 리비전과 검증은 [설치 기록](../.machine-code/evidence/installation-20260921.md)에 남긴다.

| 책임 | 적용 도구·문서 | 이번 작업에서의 경계 |
|---|---|---|
| 개발 상태·증거·재개 | `machine-code`, `.machine-code/` | 현재 프로젝트의 개발 진행만 관리 |
| 제품 요구사항 | 이 PRD, 목표 문서, 기존 실행 스킬·참조 | 제품 동작의 기준 유지 |
| 제작 단계 연결 | `harness-creator` | 아래 단계 계약을 검토하고 스킬 간 입력·출력·승인을 연결 |
| 새 스킬 작성 | 번들 `skill-creator`, 필요 시 `skill-creator2` | 사용자 승인 범위에서 작성. 실제 검토한 경험을 사용할 때만 경험 정제 흐름 적용 |
| 실제 실행·승인 | Codex와 사용자 | 별도 에이전트 런타임·세션 관리 서비스는 만들지 않음 |

현재 대화에서 직접 직렬 계획을 작성한다. 별도 planner 스킬이나 새 사용자 소유 작업을 설치·생성하지 않는다. 독립 완료 감사는 최종 프로젝트 검증 시 새 맥락의 읽기 전용 하위 에이전트로 수행한다. 실행 수단이 없으면 그 제한을 기록하고 전체 완료로 표시하지 않는다.

개발 상태는 `goal → understand → design → execute → critic → verify → handoff → complete`를 따른다. S1 승인에 따라 `design`에서 승인 범위를 기록한 뒤 `execute`로 진행한다. S1~S7의 진행과 중간 컨펌은 목표 문서에 기록하고, 전체 프로젝트 완료 전에는 마지막 상태로 이동하지 않는다.

프로젝트 루트에서 다음 명령으로 재개할 수 있다.

```powershell
$taskMachineCode = Join-Path $env:USERPROFILE '.codex\skills\machine-code\scripts\machine-code.mjs'
node $taskMachineCode status
node $taskMachineCode resume --write
node $taskMachineCode verify
```

미완료 프로젝트의 `verify`가 종료 코드 2와 `not ready`를 반환하는 것은 남은 단계·증거를 보여주는 정상 동작이다. 설치·문서 검사 통과를 제품 구현·이미지 품질 검증 통과로 바꾸지 않는다. 증거 파일을 수정하면 체크포인트를 갱신하고 해당 검증을 다시 수행한다.

이 `.machine-code/`는 개발 작업의 상태이며, §6의 제품별 자료·생성 자산 기록과 수명·용도가 다르다. Machine Code 설치 폴더와 프로젝트 작업 상태는 판매 플러그인 ZIP에 넣지 않는다.

## 12. 제작 하네스 단계 계약 — 구현 전 설계안

`harness-creator`의 단계·근거·다음 행동 기준을 적용한 제품 동작 설계다. 아래 상태명은 계약 설명이며 별도 상태 엔진을 도입한다는 뜻은 아니다. S1은 시작·자료 확인·타입 선택과 기존 경로 연결까지만 구현한다.

| 단계 | 진입·입력 | 출력·성공 근거 | 사용자 결정 | 다음 행동 | 재확인·재시도 조건 |
