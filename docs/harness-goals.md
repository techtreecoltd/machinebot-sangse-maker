# 이커머스 제작 하네스 보강 목표

작성일: 2026-09-21
상태: S8까지 main 반영 · S9 누끼 정의·합성 스튜디오컷 3장·1.17.1 배포 검증 완료 · S10 구매 결정형 FAQ 구현·1.19.1 배포 검증 완료. 과거 전체 패키지 완료 감사는 별도 미완료 상태로 보존한다.
상세 요구사항: [PRD](harness-prd.md)

## 1. 달성할 결과

사용자가 제작 용어를 몰라도 짧은 질의응답과 제품 자료 진단으로 필요한 이미지 타입을 선택할 수 있게 한다. 선택 후에는 흰색 스튜디오 제품 마스터컷, 연출·실사용컷, 효용·기능 시각화, 썸네일, 상세페이지를 각각 독립 실행하고, 필요한 경우 검수한 자산과 제품 정보를 다음 작업에 이어 쓴다.

상세페이지는 별도의 제작 스킬로 둔다. 누끼나 연출컷 제작만 요청해도 그 결과물로 작업을 완료할 수 있어야 한다. 전체 패키지는 진입 스킬이 필요한 제작 스킬을 연결하는 방식으로 제공한다.

## 2. 합의된 방향과 이번 제안

### 사용자와 합의된 방향

- 시작 질의응답으로 적합한 제작 타입을 제안한다.
- 제품 사진·누끼(흰색 스튜디오 마스터컷), 연출컷, 상세페이지의 역할을 분리하고 독립적으로 사용할 수 있게 한다.
- 목표 문서와 PRD부터 만들고 구현 범위를 작게 나눈다.
- 작업은 직렬로 진행한다. 사용자 인사이트와 설계 방향이 필요한 지점은 구체적인 제안을 보여주고 컨펌 후 진행한다.
- `techtreecoltd/machine-code`를 설치하고 그 작업 방식으로 진행한다. 현재 대화가 조정의 중심이며 프로젝트의 `.machine-code/`에 상태·근거·인계를 남긴다.

### S1 승인 범위와 후속 제안

- 첫 구현은 **S1: 시작 질의응답·추천·기존 분기 연결**로 제한한다.
- 이후 흰색 스튜디오 제품컷 → 연출컷 → 상세페이지 → 썸네일 → 효용 시각화 → 전체 연결 순서로 분리한다.
- 제품 원본·사실·자산 검수 상태를 함께 전달하는 공통 기록을 사용한다. S2 제안의 product-context.json을 사용한다.
- 시작 추천은 이유·산출물·필요 자료를 포함한 총 2~3개로 제한한다. 전체 패키지를 추천에 넣을 때도 총수에 포함한다.

2026-09-21 사용자의 “그래 그런 범위로 진행을 하자”로 S1의 최소 질문·총 2~3개 추천·기존 제작 분기 연결을 승인받았다. 후속 “작업 분기마다 깃에 푸시하고, 품질체크하고 크리틱하고 직접 결과물도 만드는 방식으로 끝까지” 지시로 합의된 S2~S7을 승인받았다. 구조를 바꾸는 새 결정이나 사용자만 아는 인사이트는 별도로 확인한다. [공수 산정](harness-effort-estimate.md)은 실측 전 계획값이며 승인 범위를 늘리지 않는다.

## 4. 범위

### 포함

- 기존 플러그인 내부의 진입 흐름과 다섯 제작 스킬 분리.
- 기존 여섯 결과물 분기 유지. 제품 사진 정리는 누끼 분기의 제품 기준컷 준비로 다루며 새 일곱 번째 분기로 추가하지 않는다.
- 명시 요청 직행, 기존 이미지 수정, 외국어 상세페이지 현지화 경로 유지.
- 공통 제품 기록과 자산 검수·인계 기준.
- 관련 실행 문서·행동 평가·배포물 동기화.

### 이번 목표 밖

- 별도 웹앱, 서버, 데이터베이스, 작업 큐, 외부 이미지 API 또는 필수 API 키 도입.
- 범용 이미지 제작 분기 추가, 브랜드 이미지 개편, 공개 디렉토리 등록.
- 모든 작업에서 누끼 → 연출 → 상세페이지를 강제 실행하는 절차.
- 매출·전환율 향상 보장이나 실제 이미지 생성 없이 생성 품질을 검증했다고 주장하는 일.

최신 실행 승인에 따라 각 단계에서 구현 → 실제 결과물 생성·검수 → 품질 검사·독립 크리틱 → 커밋·푸시 → 다음 단계 순서로 직렬 진행한다. 이미 합의된 설계의 승인은 반복하지 않는다. 미래 단계의 빈 스킬을 미리 등록하지 않는다. 아직 분리하지 않은 기능은 기존 구현으로 연결한다. 단계 안에서 발견한 범위 내 오류 수정과 검증은 재승인을 반복하지 않는다.

## 6. 컨펌 운영

- **설계 컨펌:** 사용자에게 보이는 질문·추천 방식, 스킬 책임, 기본 산출물, 후속 자동 실행 범위, 데이터 저장 방식이 바뀌기 전에 확인받는다.
- **인사이트 요청:** 타깃 고객, 실제 이용 방식, 선호 결과물 등 사용자만 판단할 수 있는 정보가 구현 결정을 좌우할 때 묻는다.
- **계속 진행 가능한 일:** 승인된 범위의 파일 편집, 문서 일치 수정, 검증, 재현된 오류 수정, 배포 ZIP 작성.
- **확인 대기 중:** 해당 결정에 의존하는 구현은 시작하지 않는다. 답변이 없거나 시간이 지났다는 이유로 승인 처리하지 않는다.
- 이 운영은 사용자가 이번 작업에서 요청한 협업 방식이다. 제품 이용자가 상세페이지 구성안을 승인하는 흐름과는 별개다.

컨펌 제안 형식:

> 이번 단계에서 바꿀 것 / 실제 대화·산출물 예시 / 추천안과 이유 / 대안의 영향 / 완료 기준을 먼저 제시한 뒤, 그 범위의 구현 여부를 확인받는다.

## 8. Machine Code 적용

- 개발 흐름은 `project`로 분류한다. 여러 제작 스킬의 경계와 이전 순서를 결정하는 작업이기 때문이다.
- 목표와 제품 요구사항의 기준은 이 문서와 PRD다. [작업 계획](../.machine-code/plan.md), [상태](../.machine-code/state.json), [인계](../.machine-code/handoff.md)는 진행을 기록하며 제품 설계를 대신하지 않는다.
- `machine-code`는 개발 상태·근거·인계를 관리하고, `harness-creator`는 제작 단계·승인·재시도·완료 기준을 연결한다. 검토한 실제 작업 예시에서 스킬을 추출할 때는 `skill-creator2`를 사용한다.
- S1 승인 기록 뒤 Machine Code의 `design`·`execute`로 진행한다. S1 완료를 하네스 전체 구현 완료로 기록하지 않는다.
- 최종 프로젝트 완료에는 실제 검증과 새 맥락의 읽기 전용 완료 감사가 필요하다. 감사 도구가 없으면 그 증거를 미확인으로 남기고 자체 점검을 독립 감사라고 바꾸어 기록하지 않는다.
- Machine Code는 이 저장소의 개발 도구다. 배포 플러그인의 필수 의존성이나 제품 이미지 생성 런타임으로 추가하지 않는다.

2026-09-21 추가 승인: S2~S7 직렬 완주·단계별 Git 푸시·품질 검사·크리틱·실제 결과물 제작. Git은 codex/ 단계별 누적 브랜치로 올리며 고객 원본과 생성물은 로컬 output/에 보관한다. 실물 원본이 없어 가상 트레이로 시험하고 실물 품질 검증과 구분한다.
