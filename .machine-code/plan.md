# Machine Code Plan

## S10 — 구매 결정형 FAQ, 2026-09-22

사용자가 이번 대화의 FAQ 수정 방향을 앞으로의 하네스에 반영하고 Machine Code 기반으로 A~Z 점검·수정하도록 승인했다. 범위는 FAQ 기획→카피→일반 상세/현지화/패키지/부분 요청 연결→호스트 렌더링→시각 검수→납품이다. 새로운 제작 분기나 별도 실행 엔진은 만들지 않는다. 현재 1.18.0의 원격 main과 작업 트리는 일치한다.

원인: 기존 문서는 마지막 FAQ 존재·사실·오탈자를 확인하지만 구매 장벽별 답변 충분성, 정보 밀도, 히어로와 다른 레이아웃을 실행 가능한 계약으로 연결하지 않았다. 독립 상세 스킬의 6/8/10 제한은 FAQ 한 장 수정/예시 요청에도 잘못 적용될 여지가 있다.

결정: 기존 공통 references에 purchase-decision-faq.md 하나를 기준 원본으로 두고 관련 진입·생성·검수 문서에서 읽게 한다. 기본은 작은 식별 컷·산세리프·얇은 구분선·답변 중심 위계이며 브랜드 지시를 우선한다. 질문은 미해결 구매 장벽과 근거로 선별한다. 앞서 만든 파우치 수정본은 시각 방향 사례이지 수납 호환이나 전환율 증거가 아니다. 사용자 정정 요약에는 개인정보·로컬 경로·터널 주소를 포함하지 않는다.

이 변경은 기존 하네스의 project 작업이다. 별도 planner 없이 메인 세션이 다음 순서를 관리한다. 전체 과거 G1~G8 프로젝트의 실패 증거는 덮지 않으며 S10 범위의 완료와 구분한다.

1. 공통 FAQ 계약과 검토된 개선 사례를 작성한다.
2. 진입·독립 상세·현지화·패키지·제품 기록·생성·검수와 README/AGENTS를 연결하고 1.19.1으로 버전을 올린다.
3. 새로운 제품을 사용한 독립 텍스트 실행으로 경로·근거 부족·브랜드 예외·단일 FAQ·기존 분기를 검증한다. 기대 답변이나 기존 결론을 실행자에게 주지 않는다.
4. 실제 호스트 FAQ 이미지를 생성하고 원본/모바일 폭을 직접 열어 검수한다. 생성 프롬프트·입력·파일 해시를 기록한다.
5. 기존 실행 검사, 원본/ZIP 해제본의 모든 스킬·플러그인·링크·바이트 일치·CRC·체크섬을 검증한다.
6. 독립 읽기 전용 완료 감사에 요구사항·변경 파일·원시 증거를 전달하고 지적 사항을 반영한다.
7. Machine Code 체크포인트·verify·handoff를 갱신한다. S10 범위와 과거 전체 패키지 미완료를 명확히 구분한다. Git 푸시는 이번 요청의 필수 완료 조건이 아니다.

완료 증거: validation/faq-forward-1.19.1.md, validation/faq-visual-1.19.1.md, validation/package-1.19.1.json, validation/critic-faq-1.19.1.md 및 .machine-code/evidence/s10-*.txt/md. 계획 문서 자체를 행동/이미지 통과로 계산하지 않는다.

## Goal

질의응답 기반 제작 타입 추천과 독립 누끼·연출·상세페이지 등 제작 스킬을 직렬 구현한다. docs/harness-goals.md의 G1~G8 및 PRD 수용 시나리오, 실제 산출물 검수, 원본·배포 검증으로 완료를 판정한다. 2026-09-21 후속 사용자 지시로 합의된 S2~S7의 끝까지 구현·단계별 Git 푸시·품질검사·크리틱·실제 결과물 제작이 승인됐다. 기존 설계의 반복 승인은 생략하고 새로운 제품 인사이트나 범위 변경만 확인한다.

S1 구현·15개 대화 실행·원본/압축 해제본 검증과 [공수 산정](../docs/harness-effort-estimate.md)을 마쳤다. ## Boundaries and decisions

개발 작업은 `project`로 분류한다. 제작 스킬 경계와 순차 이전이 필요하므로 계획은 이 메인 세션이 직접 작성한다. 별도 planner 스킬은 현재 사용하지 않으며 계획 작성을 위해 추가 도구나 사용자 소유 세션을 만들지 않는다.

하나의 플러그인과 기존 여섯 제작 분기를 유지한다. Machine Code는 개발 조정 메타데이터만 관리하며 배포 의존성이 아니다. 제품별 원본·사실·자산 기록은 승인된 S2 제안에 따라 작업 폴더의 product-context.json에 저장하고 원본·자산 해시와 직접 검수 근거를 연결한다. `harness-creator`는 PRD §12의 단계 계약에 적용한다.

S1과 후속 S2~S8 실행 승인이 확보됐다. 각 단계 시작 시 설계와 검증 범위를 알리고 같은 작업 트리에서 직렬 실행한다. codex/s1-intake에서 시작해 단계마다 이전 커밋 위에 codex/s2-cutout, s3-lifestyle, s4-detail, s5-thumbnail, s6-benefit, s7-package, s8-cg-visualization 브랜치를 만들어 일반 푸시했다. 사용자의 명시 요청으로 S8 최신 커밋을 `main`에 fast-forward 반영했다. 원격은 origin = techtreecoltd/machinebot-sangse-maker다. 고객 이미지와 생성 산출물은 output/에 로컬 보관하며 Git에는 제품 소스·검증 기록·배포 ZIP을 담는다.

실물 자료가 없어 브랜드 없는 가상 3칸 데스크 트레이를 테스트 자료로 생성한다. 합성 기준 이미지와 테스트용 설정은 실물 기능의 근거가 아니며, 실제 판매 검증과 구분한다. 테스트 범위는 누끼 1 + 연출 4 + 상세 6 + 썸네일 6 + 효용 3의 라이트 구성이다. 신규 제품·개발 구조를 추가하지 않는다.

2026-09-21 추가 설계 결정: 사용자가 사진만으로 드러나지 않는 차단·흐름·재질·신체 접촉·관심 부위·구조를 CG로 표현하는 판단이 제품 가치 전달에 필수라고 지정했다. 기존 여섯 분기를 유지하면서 공통 `cg-visualization-catalog.md`를 추가하고, 연출·효용·상세가 이를 읽어 근거가 있으면 CG 후보를 제안한다. 근거가 없으면 효과·의학적 결과를 발명하지 않고 표면 관찰·관심 부위·실제 사용 동작·확인된 구조로 표현 수준을 낮춘다. S8 합성 fixture는 이 판단과 재시도 품질 게이트를 검증하는 개발 자료이며 실제 제품 효능 증거가 아니다.

2026-09-22 사용자 정정: 누끼컷은 투명 PNG 추출물이 아니라 흰색 배경의 전문적인 스튜디오 제품컷을 뜻한다. S9에서 `machinebot-product-cutout`의 산출물 계약을 정정하고 정면·3/4·측면·상부 등 확인 가능한 다각도, 중성 화이트밸런스, 확산광, 자연스러운 접지 그림자, 불투명 흰 배경을 검수한다. 기존 S2의 투명 PNG fixture는 역사적 실패 자료로 남기고, 새 합성 트레이 studio-cutout-v2 fixture를 직접 생성·열람한다.

## Work order

1. S0: 목표·PRD와 Machine Code 설치·작업 공간 검증을 완료했다.
2. S1 사용자 승인을 목표 문서에 기록하고 `design` 체크포인트를 남긴다.
3. S1 최소 질의응답·2~3개 추천·명시 요청 직행·기존 경로 연결을 1.10.0에 구현했다.
4. S1 동작·회귀·배포와 마감 기록의 독립 감사를 완료했다. PRD §10의 S2 설계를 확인받는다.
5. S2 누끼 → S3 연출 → S4 상세페이지 → S5 썸네일 → S6 효용 시각화 → S7 전체 연결을 같은 방식으로 직렬 진행한다.
6. S8 추상 가치 CG 판단 카탈로그를 연출·효용·상세의 공통 기획에 연결하고, UV 개념·표면 접사·관심 부위 합성 fixture를 생성·열람·크리틱한다.
7. S9 누끼 의미를 흰색 스튜디오 다각도 마스터컷으로 정정하고 실제 fixture·기술 검사·직접 시각 검수를 남긴다.
8. S9 구현을 독립 읽기 전용 critic에 전달하고, 릴리스 1.17.1 원본·압축 해제본 검증과 main 반영 기록을 남긴다.
9. 전체 목표의 실제 검증 자료를 읽기 전용 독립 감사에 전달한다. 감사는 병렬 구현이나 새 사용자 소유 작업 생성을 뜻하지 않는다.
10. 전체 검증·인계가 충족되면 `verify`와 `handoff`를 거쳐 완료한다. 중간 단계 완료를 전체 완료로 기록하지 않는다.
