# Machine Code Plan

## Goal

질의응답 기반 제작 타입 추천과 독립 누끼·연출·상세페이지 등 제작 스킬을 직렬 구현한다. docs/harness-goals.md의 G1~G8 및 PRD 수용 시나리오, 실제 산출물 검수, 원본·배포 검증으로 완료를 판정한다. 2026-09-21 후속 사용자 지시로 합의된 S2~S7의 끝까지 구현·단계별 Git 푸시·품질검사·크리틱·실제 결과물 제작이 승인됐다. 기존 설계의 반복 승인은 생략하고 새로운 제품 인사이트나 범위 변경만 확인한다.

## Current situation

목표와 수용 기준은 [목표 문서](../docs/harness-goals.md)의 G1~G8, 제품 요구사항은 [PRD](../docs/harness-prd.md)가 기준이다. S1 시작 기준은 `plugins/machinebot-ecommerce-studio/`의 1.9.0 작업 트리이며 기존 미커밋 변경을 보존했다. S1 결과의 실행 원본·배포본은 1.10.0이다.

사용자는 문서 선행, 직렬 진행, 사용자 인사이트·설계 방향의 사전 컨펌을 요청했고 `techtreecoltd/machine-code` 설치·적용을 지정했다. 2026-09-21 “그런 범위로 진행”으로 PRD §4·§10의 S1을 승인했다. S1 구현·15개 대화 실행·원본/압축 해제본 검증과 [공수 산정](../docs/harness-effort-estimate.md)을 마쳤다. [1.10.0 결과](../validation/release-1.10.0-validation.md)와 마감 기록은 [독립 감사](evidence/s1-audit-final-1.10.0.md)를 통과했다. **다음 사용자 결정은 S2 제품 사진·누끼와 공통 기록 설계**다.

## Boundaries and decisions

개발 작업은 `project`로 분류한다. 제작 스킬 경계와 순차 이전이 필요하므로 계획은 이 메인 세션이 직접 작성한다. 별도 planner 스킬은 현재 사용하지 않으며 계획 작성을 위해 추가 도구나 사용자 소유 세션을 만들지 않는다.

하나의 플러그인과 기존 여섯 제작 분기를 유지한다. Machine Code는 개발 조정 메타데이터만 관리하며 배포 의존성이 아니다. 제품별 원본·사실·자산 기록은 승인된 S2 제안에 따라 작업 폴더의 product-context.json에 저장하고 원본·자산 해시와 직접 검수 근거를 연결한다. `harness-creator`는 PRD §12의 단계 계약에 적용한다.

S1과 후속 S2~S7 실행 승인이 확보됐다. 각 단계 시작 시 설계와 검증 범위를 알리고 같은 작업 트리에서 직렬 실행한다. codex/s1-intake에서 시작해 단계마다 이전 커밋 위에 codex/s2-cutout, s3-lifestyle, s4-detail, s5-thumbnail, s6-benefit, s7-package 브랜치를 만들어 일반 푸시한다. main 강제 갱신·배포·디렉토리 등록은 하지 않는다. 원격은 origin = techtreecoltd/machinebot-sangse-maker다. 고객 이미지와 생성 산출물은 output/에 로컬 보관하며 Git에는 제품 소스·검증 기록·배포 ZIP을 담는다.

실물 자료가 없어 브랜드 없는 가상 3칸 데스크 트레이를 테스트 자료로 생성한다. 합성 기준 이미지와 테스트용 설정은 실물 기능의 근거가 아니며, 실제 판매 검증과 구분한다. 테스트 범위는 누끼 1 + 연출 4 + 상세 6 + 썸네일 6 + 효용 3의 라이트 구성이다. 신규 제품·개발 구조를 추가하지 않는다.

2026-09-21 추가 설계 결정: 사용자가 사진만으로 드러나지 않는 차단·흐름·재질·신체 접촉·관심 부위·구조를 CG로 표현하는 판단이 제품 가치 전달에 필수라고 지정했다. 기존 여섯 분기를 유지하면서 공통 `cg-visualization-catalog.md`를 추가하고, 연출·효용·상세가 이를 읽어 근거가 있으면 CG 후보를 제안한다. 근거가 없으면 효과·의학적 결과를 발명하지 않고 표면 관찰·관심 부위·실제 사용 동작·확인된 구조로 표현 수준을 낮춘다. S8 합성 fixture는 이 판단과 재시도 품질 게이트를 검증하는 개발 자료이며 실제 제품 효능 증거가 아니다.

## Work order

1. S0: 목표·PRD와 Machine Code 설치·작업 공간 검증을 완료했다.
2. S1 사용자 승인을 목표 문서에 기록하고 `design` 체크포인트를 남긴다.
3. S1 최소 질의응답·2~3개 추천·명시 요청 직행·기존 경로 연결을 1.10.0에 구현했다.
4. S1 동작·회귀·배포와 마감 기록의 독립 감사를 완료했다. PRD §10의 S2 설계를 확인받는다.
5. S2 누끼 → S3 연출 → S4 상세페이지 → S5 썸네일 → S6 효용 시각화 → S7 전체 연결을 같은 방식으로 직렬 진행한다.
6. S8 추상 가치 CG 판단 카탈로그를 연출·효용·상세의 공통 기획에 연결하고, UV 개념·표면 접사·관심 부위 합성 fixture를 생성·열람·크리틱한다.
7. 전체 목표의 실제 검증 자료를 읽기 전용 독립 감사에 전달한다. 감사는 병렬 구현이나 새 사용자 소유 작업 생성을 뜻하지 않는다.
8. 전체 검증·인계가 충족되면 `verify`와 `handoff`를 거쳐 완료한다. 중간 단계 완료를 전체 완료로 기록하지 않는다.

## Verification

S0: 설치한 세 스킬의 `quick_validate.py`, CLI 도움말 실행, 설치 파일과 지정 Git 리비전 대조, 프로젝트 `init`·`status`·`resume`, 문서 링크와 기존 제품 파일 보존 검사. 설치 근거는 [설치 기록](evidence/installation-20260921.md)에 남긴다.

S1 이후: PRD §9의 단계별 대화 사례와 실제 이미지 검수, 프로젝트 AGENTS.md의 원본·압축 해제본 검사, 링크·버전·ZIP·체크섬 검사. 기록은 실제 실행 범위를 명시하고 실패·미확인·오래된 근거를 통과로 바꾸지 않는다.

최종 `project` 완료에는 plan·implementation·critic·verification·handoff 근거가 모두 필요하다. S1만 마친 시점에도 S2~S7이 남으므로 `verify`의 `not ready`와 종료 코드 2가 예상된다. S1의 행동 검증·감사는 전체 프로젝트 감사와 구분해 기록한다.
